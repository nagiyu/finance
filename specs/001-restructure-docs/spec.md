
# Feature Specification: ドキュメント構造化とドキュメント駆動開発の整備

**Feature Branch**: `001-restructure-docs`  
**Created**: 2025-11-27  
**Status**: Draft  
**Input**: User description: "docs 配下のドキュメントを整備してください。現状、様々なタスクで生成されたドキュメントが乱立しており、煩雑になっています。また、現行のコードに正しく追従できていないところもあります。正しく構造化し、ドキュメント駆動開発が進められる状態にします。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Developer authoring (Priority: P1)

新しい機能や変更を実装する開発者が、コード変更に合わせて正しい場所にドキュメントを作成・更新できる。

**Why this priority**: ドキュメントがコードと乖離すると品質維持が難しくなるため、まずは開発フローに組み込むことが最優先。

**Independent Test**: 開発者が既存のリポジトリで1つの機能変更を実装し、提示したテンプレートに従ってドキュメントを追加・更新できること（手順を1つ選んでレビューで検証）。

**Acceptance Scenarios**:

1. **Given** 開発者が機能を追加するブランチを作成している、 **When** ドキュメントを追加/更新しプルリクエストを作成する、 **Then** レビュアーは該当するドキュメントが新しい構造（トピック分類 + 所有者）に従って配置されていることを確認できる。
2. **Given** 既存のドキュメントが複数の場所に分散している、 **When** リファクタリング手順（ドキュメント移動）を実行する、 **Then** 重複が削減され、主要な参照先が1つに集約されている。

---

### User Story 2 - Reviewer and new team member discovery (Priority: P2)

レビュアーや新しく参加したメンバーが、ある機能やコンポーネントに関する情報を30秒以内に見つけられる（目標値はSuccess Criteriaで定義）。

**Why this priority**: ドキュメントの可読性・検索性が改善されるとオンボーディングとレビュー効率が向上するため優先度は高いが、まずは作成フローの整備が先。

**Independent Test**: 代表的な調査タスク（例：MyTickerサービスの設定手順を見つける）を与え、所定の時間で正しいドキュメントへ辿り着けるかで評価する。

**Acceptance Scenarios**:

1. **Given** 新しいメンバーに「特定機能のセットアップ手順を見つける」というタスクを与える、 **When** そのタスクを実行する、 **Then** 90%以上のケースで30秒以内に正しいドキュメントに到達できる。

---

### User Story 3 - Documentation maintainers (Priority: P3)

ドキュメント所有者が自分の担当領域を把握し、定期的にドキュメントの整合性チェックと更新を行える。

**Why this priority**: 継続的なメンテナンスは重要だが、まずは流入地点・構造を整備することが先行する。

**Independent Test**: 所有者がリストアップされた自分のドキュメントをレビューし、5件の更新作業を完了できるかで評価する。

**Acceptance Scenarios**:

1. **Given** ドキュメント所有者一覧が作成されている、 **When** 所有者が月次レビューを実施する、 **Then** 期限内に必要な更新が行われる。

---

### Edge Cases

- 生成物（自動出力される大量のログやバイナリ）や大きなデータダンプを `docs/` に置いてしまうケースの扱い
- 多言語（README やドキュメントの英語/日本語の差分）による重複
- 外部にホストされたドキュメント（Wiki、Confluence等）との整合性

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: リポジトリ内のドキュメントを一貫したトピック階層（例：`docs/<area>/<topic>/...`）へ整理するためのガイドラインを作成する。
- **FR-002**: 新規ドキュメントのテンプレート（目的、前提、手順、テスト/確認方法、担当者）を定義し、`docs/` 配下に配置する。
- **FR-003**: 既存ドキュメントを調査し、重複・散在している文書をリスト化して移行計画（移動、統合、アーカイブ）を作成する。
- **FR-004**: 各ドキュメントに**所有者（担当者）**を明記するメタ情報を必須とする（例：ファイル先頭に担当者欄を追加する）。
- **FR-005**: ドキュメント更新フローを定義し、コード変更とドキュメント更新を紐付けるレビューチェックリストを作る（プルリクエストテンプレートにドキュメント更新チェックを含める等）。

### Quality & Constitution Requirements (mandatory)

- **Q-001**: ドキュメントは Markdown 形式を標準とする（既存の特別なフォーマットは個別判断）。
- **Q-002**: テンプレート、命名規則、トピック分類を文書化して `docs/` に保存する。
- **Q-003**: テスト可能な検証方法（例：ドキュメント一覧に対するマニュアル/自動チェックリスト）を用意する。
- **Q-004**: 主要コンポーネント（MyTicker, Finance API 等）について、1つの主要ドキュメント（single source of truth）を定義する。
- **Q-005**: 既存コードとの整合性確認項目を作成し、少なくとも主要5ファイル/モジュールについてドキュメントのトレースバックができること。

### 対象範囲（確定）

決定: リポジトリ全体のドキュメントを対象とする方針を採るが、**ユーザーが常に `docs/` 直下から辿れる構造を必須**とする。具体的には:

- ルートの `docs/` が目次（index）として機能し、`finance/`, `client/`, `server/` 等の主要領域へのリンク（および各領域の概要）を含める。
- 各領域の詳細ドキュメントは当該サブディレクトリ内に保持する（例: `docs/finance/` はハブとして、実際の詳細は `finance/` 内の README や `finance/docs/` を参照する）。
- 移行作業ではまず `docs/` と `finance/`、`client/finance`、およびルート README を優先して調査・統合する。

この方針により、検索性と一貫性を保ちつつ既存のサブディレクトリ構造を尊重できます。

### アーカイブ vs 統合の方針（確定）

決定: 重複ドキュメントは**統合して古いものは積極的に削除**する方針とする。ただし、削除前に以下を実施する:

- 統合先を明確に定義し、移行ログ（`specs/001-restructure-docs/migration-plan.md`）に変更履歴と理由を残す。
- 重要な履歴が必要な場合のみアーカイブを行い、通常は Git の履歴で過去バージョンを追えるためリポジトリ内に冗長なアーカイブを残さない。
- 統合/削除はレビューと担当者承認を必須とする（プルリクエストで明示）。

この方針によって重複の解消と参照先の一本化を優先し、余分なドキュメントの蓄積を防ぎます。

## Key Entities *(include if feature involves data)*

- **Document**: Markdown ファイル。属性: `title`, `area/topic`, `owner`, `last-updated`, `related-code-paths`。
- **Topic/Area**: ドキュメントの分類（例：`finance`, `client`, `guides`）。
- **Owner**: ドキュメントの責任者（個人またはチーム）。
- **Spec/Checklist**: 移行・品質チェック用の一覧（CSV/Markdown で管理）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 対象としたドキュメントのうち、少なくとも90%が新しいトピック階層にマッピングされ、主要ドキュメントが1箇所に集約されていること（検証は移行一覧で確認）。
- **SC-002**: 新メンバー（少なくとも3名）に対する探索タスクで、90%のケースで30秒以内に正しいドキュメントへ到達できること（ユーザーテストによる計測）。
- **SC-003**: 重複・古いドキュメントのうち、80%以上が移行（統合またはアーカイブ）方針に従って対処されること。
- **SC-004**: ドキュメント更新チェックリストが導入され、以降のプルリクエストでドキュメント更新が必要なケースのうち95%でチェックが行われること（レビュー記録で確認）。

## Assumptions

- ドキュメントは Markdown で管理する。既存の外部システム（Confluence 等）は移行対象外だが、必要に応じリンクを残す。
- 重大な法的/コンプライアンス要件は本作業の範囲外。
- 初期フェーズでは手動レビュー中心とし、必要に応じて自動チェックを後続で追加する。

## Out of Scope

- Confluence や外部 Wiki の大規模移行（リンクの追加や参照は行うが完全移行は別作業）。
- ドキュメントの全文自動翻訳や多言語対応は今回の対象外（必要な場合は別タスク）。

## Deliverables

- `docs/` に保存されたドキュメント構造ガイドライン（テンプレート含む）。
- `specs/001-restructure-docs/checklists/requirements.md`（仕様品質チェックリスト）。
- 移行計画（移行対象一覧、担当者、優先度）を含む `specs/001-restructure-docs/migration-plan.md`（初版）。
